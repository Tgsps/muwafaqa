## Context

The project specification asks for alerts on contract renewals and on obligations. The data model lists "Obligation" (child table of the contract), "Renewal Type" and "Notice Period" as later items (`docs/data-model-phase1.md`, priority 3). **Today neither the Obligation table nor the columns "renewal type" and "notice period" exist on the contract** (script, schema read); `mwf_expirydate` (Date Only) and the status In Force exist.

Two alerts need a record that "this alert was already sent":

- the **Contract State Guard** (ADR-004) blocks edits to an approved contract, so a claim column such as `mwf_remindedon` **cannot live on the contract** (it would be rejected, or it would need a bypass);
- **overlapping runs were measured on 2026-10-29**: runs of 16.6 to 84.8 s on a 1-minute interval (script, flow document section 8). Two runs can look at the same candidate.

## Decision

1. **Table `mwf_obligation`** (audit ON): `mwf_contract` (lookup to the contract, DELETE cascade), `mwf_party` (Choice: First Party, Second Party), the description (the primary name column `mwf_name`), `mwf_duedate` (Date and Time, user-local behavior as `mwf_decidedon`, so stored in UTC), `mwf_status` (Choice: Open, Done, Disputed). **"Overdue" is not stored**: it is derived (Open and `mwf_duedate` before now).
2. **Table `mwf_alertlog`** (service table, **audit OFF**, **no project role gets any privilege on it, in particular no delete**): one row per alert. One string column `mwf_alertkey`, set to required level ApplicationRequired (**measured: the server does NOT enforce that level for a Web API write**, see "The null and empty key problem") with an **alternate key** `mwf_AlertLogKey` on it. The primary name column `mwf_name` is required by the platform; the flow writes the same text into it, for people only.
3. **The key:** `<sourceGuid>-<TYPE>-<yyyyMMdd>`. TYPE is one of `OBLIGATION-DUESOON`, `OBLIGATION-OVERDUE`, `RENEWAL-T90`, `RENEWAL-T30`. The date is the **due date** (obligations) or the **expiry date** (renewal), so **a changed date gives a new key and the alert is armed again**. The key must **never contain** `/ \ < > * % & : ? + #` and must **never be null or empty**. Builder and validator: `scripts/lib/alert-key.mjs` (unit tested, one test per forbidden character).
4. **Claim = INSERT the AlertLog row first, then send.** A duplicate-key rejection means "already claimed: skip, send nothing". **Concurrency Control is not used** (Learn: it cannot be undone, and removing it needs deleting and re-adding the trigger) **(from Learn, as stated; not re-read in this session)**; the alternate key does the work that the setting would have done.
5. **Duplicate detection reads the error code in the BODY of the response** (`DuplicateRecordEntityKey`, `0x80060892`), **not the HTTP status**. Learn does not document the HTTP status for this error, and its pages disagree for a different duplicate mechanism (412 against 500) **(from Learn, as stated; not re-read in this session)**. **Measured once (2026-11-03, direct Web API): HTTP 412 with code `0x80060892`** (raw values in "Measured results of the uniqueness test"). The status is undocumented and was measured once, so the design does not rely on it. **Decision for the flow (2026-11-03): fail closed.** No email unless the claim insert succeeded; **any** failure of the insert (412 or anything else) skips the send and is recorded separately in the run (the outputs of the failed action are stored in a Compose action, a counter is incremented). The flow does not branch on the code `0x80060892`. Whether the flow can read the real output of a failed insert, whether the connector retries it and whether a handled failure still marks the run Failed are **unknown until test case 13** of `docs/flow-obligation-alerts.md` (an alert log row inserted before the window). No separate discovery flow.
6. **The key index is built asynchronously** (Pending, In Progress, Active, Failed; `ReactivateEntityKey` exists) **(from Learn, as stated; not re-read in this session)**. **Every script and every flow run must refuse to run unless `EntityKeyIndexStatus` is Active.** The scripts do (`keyGate`, unit tested); the flow must do the same before its first claim (not built). After a solution import the key is not in effect until the background job has finished (**not tested here**).
7. **Renewal alerts:** only contracts **In Force**; a contract whose renewal type is none is skipped; the **notice deadline = expiry date minus the notice period in days**; two alerts, at **90 and 30 days BEFORE THE NOTICE DEADLINE** (owner's interpretation). The alternative, counting the 90 and 30 days from the **expiry date**, is **recorded as not chosen**.
8. **Recipient:** the **owner of the contract**, always (also for obligations of the second party). **Disputed obligations are not alerted.** Due dates are entered by hand as **final dates**; there is no working-day calendar.
9. **Parameters:** the due-soon **lead time**, the **lookback window** and the **recurrence interval** are **required named parameters per variant with no default in code**. **Test variant (test constants, not business values): lead 5 minutes, lookback 30 minutes, interval 1 minute**, chosen so that seeded rows fall inside or outside the window within one test window. **Production variant: OPEN QUESTION for the owner for all three; no number is proposed here**, and the generator refuses to emit a production definition without them. **The query only considers Open obligations whose due date lies in `[now - lookback, now + lead]`** (decision of 2026-11-03). **No new column on Obligation.** **Cost, accepted:** an obligation that has been overdue for longer than the lookback window because the flow was down never gets its alert (and a due-soon alert is lost if the downtime outlasts the lead time). The lookback also stops old, already-alerted obligations from being re-read and re-attempted forever; inside the window they still are, and more than 50 inside the window hide the rest (`$top`).
10. **Cap of 5 notices per run** and **informational emails only**, as in ADR-010. **An alert never approves, rejects or changes anything.**

## The null and empty key problem

Learn: uniqueness of an alternate key is **not enforced on NULL** **(from Learn, as stated; not re-read in this session)**. The same effect was seen in this project: the server **accepted an empty role** in an Approver Assignment row on 2026-10-25 (script, ADR-009, "Create of the row without a role"). The column `mwf_alertkey` is set to the required level **ApplicationRequired**. **Measured on 2026-11-03: that level is NOT enforced for a write through the Web API.** The server accepted an empty-string key twice (HTTP 204, two rows) and a null key twice (HTTP 204, two rows). So **the alternate key gives no protection against an empty or a null key**, and a flow that sends one creates a row that never blocks anything. Defences: the key builder refuses null and empty; the flow must guard against an empty or out-of-length key **before** the insert (section "Key construction in the flow"). The earlier observation (the empty role of an Approver Assignment, ADR-009) was on another column; this measurement is on `mwf_alertkey` itself.

## Alternatives rejected

| Alternative | Why rejected |
|---|---|
| **Claim columns on the contract** (as `mwf_remindedon` on the step) | The Contract State Guard blocks edits to approved contracts (ADR-004). A bypass for a flow would weaken the guard the project built on purpose. |
| **Claim columns on the obligation** | Works for obligations, but not for renewals (those are on the contract), so there would be two mechanisms. |
| **Concurrency Control = 1 on the trigger** | Irreversible without deleting and re-adding the trigger **(from Learn, as stated; not re-read in this session)**. The alternate key protects every writer of the log, not only this flow, and does not depend on a trigger setting. |
| **Send first, then write the log** | Can send twice; same trade-off as ADR-010. |
| **A lookup to the source instead of a text key** | A key over a lookup and two more columns would need those columns for two different source tables (contract, obligation); a single text key is simpler and its alternate key is one column. Cost: orphan rows (see the risks). |

## Trade-offs

- **A text key instead of a lookup:** one table and one key for both sources, against no cascade delete (orphan rows stay) and no referential integrity.
- **The date in the key:** a changed due or expiry date re-arms the alert (wanted), against a **second alert for the same obligation when someone edits the date back and forth** (each date has its own row).
- **No delete privilege on the log:** a row cannot be removed by a project role, so an alert cannot be re-sent by accident, against rows that stay forever (growth is not measured; there is no clean-up job).
- **The owner receives every alert** (also for second-party obligations): one rule, against alerts about things the owner of the contract does not control.
- **The production lead time has no default:** a missing value stops the flow instead of silently using a number nobody chose.

## Known risks

- **The key cannot be checked from inside the flow (accepted, documented risk, 2026-11-03):** as far as we know the flow cannot read `EntityKeyIndexStatus`, so an insert while the key is Pending or Failed (for example right after a solution import) would succeed twice and protect nothing. Mitigation by procedure: before turning the alerts flow on after an import, check that `mwf_AlertLogKey` is Active (`docs/rebuild-runbook.md`, step R16b, **[NOT TESTED]**). Nothing in the flow protects against it.
- **A lost alert:** if the send fails **after** the claim, the alert is lost (the log says it was sent). Accepted, as in ADR-010.
- **Orphan AlertLog rows** after deleting a contract or an obligation: the key is text, not a lookup. **Tests must clean them** (the uniqueness test sweeps by the `TEST-TMP-ALERT-` prefix).
- **Deleting a log row re-fires the alert.** That is why no project role has the delete privilege.
- **Import untested:** whether the alternate key is active and the privileges are right after a solution import has not been tested (the project has never imported its solution).
- **The HTTP status of the duplicate rejection was measured once (412, direct Web API)**; it is undocumented, so the design reads the code in the body. It has not been seen inside Power Automate.
- **Learn pages disagree on the default degree of parallelism** **(from Learn, as stated; not re-read in this session)**. Irrelevant here: the design does not depend on it and does not use Concurrency Control.
- **The renewal alerts depend on columns that do not exist** (renewal type, notice period): they need their own schema step and their own ADR note once the owner approves their shape.
- **A notice deadline already past** when a contract enters In Force (for example 20 days left: both the 90-day and the 30-day point are behind): not decided (open question 3).
- **Overlapping runs** can still make two runs reach the same candidate; the alternate key rejected 4 of 5 parallel inserts of one key in the direct Web API test (one run, N = 5); **not seen from two real flow runs**.

## Not proven

**Measured: the tables and the key (see "Findings of the first apply") and the uniqueness behavior through the direct Web API (see "Measured results of the uniqueness test"), each from ONE run.** Still unproven: that a flow can read the error code of a failed insert and take the duplicate branch (not seen inside Power Automate), concurrent inserts from two real flow runs (the test used 5 parallel requests from one client), the behavior with more than 5 parallel inserts or on repeated runs, the effect of a solution import, and every alert rule (the flow exists but has never been turned on).

## Open questions

1. **Production due-soon lead time, lookback window and recurrence interval** (owner). No numbers are proposed. The lookback decides which downtimes lose alerts.
2. **Overdue behavior:** the key gives **one** OVERDUE alert per due date. Whether the owner wants repeated overdue reminders is not decided; repeats would need a different key (for example a week number), not designed here.
3. **A notice deadline that is already past** when the contract enters In Force: alert once for the latest missed point, for both, or for none?
4. **Roles for `mwf_obligation`** (who creates and edits obligations): not designed. The table is UserOwned like the contract; ADR-008 has no row for it.
5. **The columns "renewal type" and "notice period"** on the contract: names, types and values are not designed (a "none" value of the renewal type is assumed by decision 7).
6. **Who should receive alerts** if the contract owner leaves or is disabled: not decided (same kind of question as A1 in ADR-010).

## Measured results of the uniqueness test (2026-11-03)

**Limits, read first:** ONE run; N = 5 parallel requests; **direct Web API calls from one script only** (not Power Automate, not two separate clients); the table is configured audit OFF; the environment is a single development environment. These values were measured, not derived. The test is `scripts/test-alertlog-uniqueness.mjs`; it wrote only rows whose name and key start with `TEST-TMP-ALERT-` and deleted the 6 rows it created (final count of such rows: 0; baseline 11 / 110 / 5 / 0 afterwards).

| Case | Raw result from the server |
|---|---|
| First insert of a new key | HTTP **204** (row created; readable by its alternate key, HTTP 200) |
| Same key again | HTTP **412**, body `{"error":{"code":"0x80060892","message":"Entity Key Alert Log Key violated. A record with the same value for Alert Key already exists. A duplicate record cannot be created. Select one or more unique values and try again."}}`; exactly one row holds the key afterwards |
| 5 parallel inserts of one new key | **1 success** (204) and **4 failures**, each HTTP **412**, code `0x80060892`, the same message; exactly one row holds the key afterwards |
| Empty-string key (`""`), insert 1 and insert 2 | HTTP **204** both times; **two rows created** |
| Null key, insert 1 and insert 2 | HTTP **204** both times; **two rows created** |
| Audit records for the 6 test rows | **0** (observation; the table is audit OFF) |

What follows from it, and what does not:
- **Follows:** the alternate key rejects a duplicate non-empty key, also under 5 parallel requests, with the code in the body; the status was 412 in every rejection of this run. **ApplicationRequired is not enforced for Web API writes** on `mwf_alertkey`, and an empty or null key is **never rejected as a duplicate** (two empty keys coexisted). An empty or null key therefore blocks nothing.
- **Does not follow:** that Power Automate sees the same status and body (the Dataverse connector may present a failed insert differently; not seen); that 412 is stable (undocumented, one run); that the result holds for N above 5.

## Key construction in the flow

The flow cannot import `scripts/lib/alert-key.mjs`. The rule, to be kept by whoever builds it:
1. **The flow generator emits the key expression.** The expression is written once, in the generator, from the same parts as `alert-key.mjs` (lower-case source GUID, the TYPE, `yyyyMMdd` of the due date or the expiry date, joined by `-`); nobody types it into the designer.
2. **Offline tests compare the expression's output with `alert-key.mjs` on samples** before any build is applied: a lower-case GUID (and one given in capitals), a date as `yyyyMMdd`, **every TYPE** (`OBLIGATION-DUESOON`, `OBLIGATION-OVERDUE`, `RENEWAL-T90`, `RENEWAL-T30`), an end-of-month and a leap-day date. The comparison needs an evaluator for the Power Automate expressions used; if there is none, that gap is stated, not hidden.
3. **The flow must guard against an empty or out-of-length key before the insert**, because the server accepts empty keys (measured above). The guard: the key is not empty, is not longer than 100, and (as far as the expression language allows) matches the shape `<guid>-<TYPE>-<yyyyMMdd>`; on failure nothing is inserted and nothing is sent. The guard is part of the flow, not of the server.
