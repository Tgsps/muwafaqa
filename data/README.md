# Test data

All data in this folder is **entirely fictitious**: fake company names (each carries a "Test" or "Fictional" marker), fake registration numbers (`TEST-CR-####`), emails on the reserved `example.com` domain, invented contract values. Do not replace anything with real data.

| File | Rows | Target table |
|---|---|---|
| `counterparties.csv` | 5 | Counterparty (`mwf_counterparty`) |
| `contracts.csv` | 10 | Contract (`mwf_contract`) |
| `approval-matrix.csv` | 110 | ApprovalMatrix (`mwf_approvalmatrix`), see "Approval matrix" below |

CSV headers match the schema names in [docs/data-model-phase1.md](../docs/data-model-phase1.md). Choice and Status Reason columns hold **labels**, not numeric values (the numeric values are generated by Dataverse). The Counterparty and Currency columns hold **names**. The loader script resolves those names. The maker import wizard does **not** accept them (see "Do not use the import wizard").

## How the data is loaded (supported way)

Use [`scripts/load-test-data.mjs`](../scripts/load-test-data.mjs). It uses the Dataverse Web API and the device code sign-in (it prints a URL and a code; the token stays in memory).

```
node scripts/load-test-data.mjs --env=https://<org>.crm4.dynamics.com [--skip-pending]
```

What the script does (read from the script):
- **Idempotent.** Counterparties are keyed by name and contracts by Contract Number. An existing row is skipped, never changed.
- **Lookups by name are resolved by the script.** The Counterparty is found by its name among the loaded counterparties. The Currency name is mapped to an ISO code (USD, KWD, AED, SAR) and matched with the **existing** currency record. It never creates or changes currency records, and it stops if one of the four is missing.
- **Choice labels** are resolved from the table metadata, with no hard-coded numbers.
- **Statuses:** only **Draft, In Force and Rejected** are produced. The three contracts whose CSV status is Pending Approval (`TEST-CT-0002`, `0006`, `0010`) are loaded as **Draft** (with `--skip-pending` they are skipped). In Force and Rejected are set by an update after creation and verified by reading the row back.
- **No base amount is computed.** Dataverse calculates `mwf_value_base` from the currency records.

Result of the run on 2026-10-06: 5 counterparties and 10 contracts created. A check on 2026-10-07 compared the 30 date cells of the loaded `TEST-CT-*` rows with `contracts.csv`: **30 of 30 identical**, so dates sent through the Web API are exact.

The statuses in the live environment have changed since (approval flow tests and manual actions). The table at the end shows what the loader loads, not the current state.

## Do not use the import wizard with these files

Tested on 2026-10-07 with small temporary files that are not in the repository. Evidence: item 8 and the Results log in [docs/verification-checklist.md](../docs/verification-checklist.md).

1. **Every lookup column needs a GUID.** The Counterparty by name failed: " Demo Partner Holdings Test Inc is not a valid primary id Guid value." The Currency by name failed the same way: " US Dollar is not a valid primary id Guid value." With GUIDs, both mapped correctly. GUIDs are specific to one environment, so a CSV with GUIDs does not belong in the repository.
2. **`statuscode` is ignored at creation.** The file said Draft, In Force, Rejected, Draft. All four rows were Draft.
3. **Date Only values shift one day back.** All 10 non-empty date cells were stored one day earlier than in the file. The cause is not confirmed.
4. KWD `750.125` was stored with three decimals (this import used GUIDs).

## Warnings

- **The environment base currency is TRY** (Turkish Lira), not USD. Base amounts (`mwf_value_base`) are in TRY. The 100,000 USD authority threshold is in US dollars, so Phase 2 must compute a separate USD value. The contract values in `contracts.csv` were designed under the earlier USD-base assumption and were **not recalculated** for TRY, so the "just below / just above 100,000 USD" cases no longer hold.
- **Exchange rates are placeholders**, used for demonstration only. They are not market rates.
- **KWD has 3 decimal places** (ISO 4217); the other currencies here use 2. Verified through the Web API on 2026-10-07: KWD `6500.255` is stored as is, and USD `100.255` becomes `100.26`. What the form and the grid display was **not** checked.
- **Approval flow:** the loader never sets Pending Approval, so by design it does not start approval runs. Setting a contract to Pending Approval later does start the flow.

Verified by test: the convention is **base amount = value ÷ rate**, so the rate is the number of units of the currency per 1 unit of the base currency. 100 USD gave 4,900 TRY and 100 KWD gave 15,000 TRY. Implied cross rates are about 3.77 AED/USD and SAR/USD, and 0.327 KWD/USD.

## Approval matrix (`approval-matrix.csv`)

**Fictional bands, to be replaced when the real thresholds are known.** They show the structure only.

Columns: `mwf_rulename`, `mwf_contracttype`, `mwf_contractdirection`, `mwf_minvalueusd`, `mwf_maxvalueusd`, `mwf_steporder`, `mwf_approverrole`, `mwf_actiontype`. Choice columns hold **labels**. The loader resolves them to values from the table metadata.

**Convention:**
- **Min is exclusive, Max is inclusive.** A contract of value `v` is in the band where `Min < v <= Max`.
- **An empty Max means unbounded** (no upper limit).
- **A value of exactly 0 is excluded**: it falls in no band, because the first band starts at Min 0 (exclusive).
- Min and Max are in **US dollars**. They are meant to be compared with the independent USD value that Phase 2 computes, not with the TRY base amount. That comparison is not implemented yet.
- `mwf_steporder` is the approval step within a band (1, 2, ...). `mwf_actiontype` is Approve or Inform.

| Band | Min (exclusive) | Max (inclusive) | Steps |
|---|---|---|---|
| 1 | 0 | 10,000 | 1 Department Head (Approve) |
| 2 | 10,000 | 50,000 | 1 Department Head, 2 Finance Manager (Approve) |
| 3 | 50,000 | 100,000 | 1 Department Head, 2 Finance Manager, 3 General Manager (Approve) |
| 4 | 100,000 | empty | 1 Department Head, 2 Finance Manager, 3 General Manager, 4 Regional Office (Approve), 5 Owner (**Inform**) |

The same four bands apply to each of the 10 combinations (5 contract types x 2 directions): 11 rows per combination, **110 rows**. The Rule Name format is `<Type> - <Direction> - Band <n> - Step <k>` (no slash).

**Loader:** [`scripts/load-approval-matrix.mjs`](../scripts/load-approval-matrix.mjs) has three modes: `check` (read only, compares the live column names, types and option values with the expected list and reports each RequiredLevel), `load` (needs `--confirm-mutates-environment`, idempotent, looks up by Rule Name and skips existing rows), and `validate` (read only).

**Result of the run on 2026-10-11:** `check` passed. The first `load` created 110 rows, a second `load` created 0 and skipped 110. `validate` passed: 110 rows, 10 combinations, 40 bands contiguous with no gaps or overlaps (first Min 0, last Max empty), step orders 1..n in every band, and exactly one Owner/Inform row per combination, in the top band.
